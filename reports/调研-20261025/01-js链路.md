## 0. 结论速览（先看这 7 条）

1. **评估链路的「采集→合并」部分是可靠的，但「榜单→账号」的语义映射层是残的**。`plan5-core.js` 把榜单 101 支队伍里的 **38 支（37.6%）变成了结构性不可组**：12 支被 `司马懿/弓诸葛` 整队跳过（`plan5-core.js:176,208`），19 支因武将别名缺失、7 支因版本标记（`弓`/`新`）在上游根本没有生产者。详见 §4 P0-1/P0-2。
2. **「完整落地」在数据上几乎不可能发生在高档队伍**：全部 186 账号合计只有 111 支「完整」队，其中 `T2-` 64 支、`T1` 45 支、`T0` 1 支、`T0+` 1 支；根因是战法/宝物别名层残缺（战法 34/101 token 未映射、宝物 9/25 token 从未命中）。仅补齐 9 个战法别名 + 5 个宝物别名，全局可完整队伍就从 **29/101 升到 78/101**（`T0+` 1→3，`T0` 3→18）。详见 §4 P0-3。
3. **自动购买建议（`recommend.js`）系统性漏号**：`land-stats.js:27-29` 与 `plan5-node.js:25-27` 仍按 `server-price` 去重，把 186 号压成 163 号（与 `docs/最终购买建议-20260810-自动.md:3` 的「163 个账号」吻合），被丢的 23 个号里含 15 支完整队、2 个「完整 3 队」的号（如 `X5882 ¥1,500`）。同一去重缺陷在 `cbg-detail-extract.js:242` 被 copilot 记录为已知事故，但分析阶段没改。详见 §4 P0-4。
4. **`quality===5` 过滤方向正确但边界没做**：`merge-api.js:71-77` 不再用名字白名单（对的），但没有应用 copilot 明确列出的噪声名单，`data/accounts-api.json` 里 **1318/13236 张 quality=5 卡是侍卫/麦子/陶渊明等噪声**，129/129 个号都带噪声，**33 个号的「五星≥85」是噪声凑出来的**；而 CBG 的 `desc_sumup_short` 五星数恰好等于含噪声的 quality=5 数量（逐号相等），说明这条阈值从未真正筛过「真实五星」。详见 §4 P0-6。
5. **评分/排序实现与文档三方不一致**：档位权重 `T0+` 代码 8、`T0` 7、缺 `T0-`（`plan5-core.js:179`），文档是 `T0+=10 / T0-=6 / T1=3 / T2-=1`；`recommend.js:70-72` 排序只用「完整×1000+只缺宝×100+可组」，`武将分` 与价格都不参与，却在 `recommend.js:80` 与 copilot 第 33 行声称参与/「优先选便宜的」。且 `recommend.js:45-49,62` 用 `server-price` 作分数键，186 行分析结果只有 163 个键、18 组冲突（如 `X5882-2000=[90,68]`），分数会串号。详见 §4 P0-5/P1-2/P1-7。
6. **两份「一键」入口都不可信**：`find-all.ps1:28,34` 传给 `api-collect.js` 的 `$browserArg` 带前导空格+字面引号，实测 node 收到的是 ` "C:\...\json"`（含引号），`api-collect.js:157` 的 `fs.existsSync` 必然 false → **「补漏模式」静默失效**；`package.json:7-8` 的两个 npm scripts 路径都少了 `scripts/`，`npm run extract/analyze` 直接找不到文件。详见 §4 P1-6/P1-8。
7. **本链路当前只有 2 支 T0+/T0 能真正「完整」**（`T0 螃蟹队`@X5862、`T0+ 胖章鱼`@X5864）。也就是说 `docs/最终购买建议-20260810-自动.md` 的 Top10 里「完整队」全是 T1/T2-，不是数据里没有高档号，而是高档队被别名/标记/跳过规则挡在了落地判定之外。这与仓库「第二轮只对 shortlist 复核战法宝物、区分到手即战力」的设计目标直接冲突。

### 2.3 数据形态不匹配点（迁移风险）

- **价格三套单位/类型**：采集是「分」`number`（`api-collect.js:78`、`find-all.ps1:19-20`），合并后是「元」`string`（`merge-api.js:78-79`），`recommend.js:18-19` 的 CLI 又是「元」`int`，而 `parse-questionnaire.js:39-41` 的预算映射回到「分」；`land-stats.js:13-14,31` 的 `FILTER_PRICE` 还是「带逗号字符串严格相等」。任何一处换单位都不会报错，只会让筛选静默错档。
- **`overview.server` 语义漂移**：API 原始 `server_name` 是「X5860 决胜中原(赛季已开启15天)」（实测），`buildResult` 用 `replace(/(X\d{4}).*/, '$1')` 截成 `X5860`（`api-collect.js:73`），合并时又写回 `list.server`（`merge-api.js:82`）；浏览器路径的 server 来自页面正则（`cbg-detail-extract.js:56-61`），可能为 `null` → 下游 key 出现 `null-1,500`。
- **`marks` 双 schema**：浏览器路径是「阵营+版本」字符串（可含 `|`），API 路径是单元素数组，且 SP/XP 版本把「阵营」槽位占了（`SPSP`、`XPXP`）。下游 `plan5-core.js:168-169` 用 `Array.isArray` 兼容，但 `browser-verify.js:112` 只取 `marks[0]`，会丢同名异版本的第二条标记。

## 3. 核心算法

### 3.1 榜单解析 `initTeams()`（`plan5-core.js:62-104`）

1. **速览作白名单**：正则 `/^\|\s*(T0\+|T0-|T0|T1|T2-)\s*\|\s*(.+?)\s*\|\s*$/` 抓 `## 速览` 表（`:65-69`），得 `summary = {T0+:10, T0:20, T1:35, T2-:41}`（实测）。
2. **正文建队**：扫 `## 分档` 切档（`:73-75`）；`### 队名` 清洗（`：`后缀、`^\d+[.、]`、全角括号注，`:78-83`）；**只有队名在速览名单里才接受**（`:84`）。
3. **三行成队**：表行正则 `/^\|\s*([^|]+?)\s*\|([^|]*)\|([^|]*)\|([^|]*)\|/` 取「武将/第二战法/第三战法/宝物」4 列（`:90`），攒满 3 个武将 push 一队（`:96-99`）。

实测：106 个 `###` 全部被接受，得到 **101 队**；差的 5 队是 `T1 王异法刀/变种钱步/多马队/丑刀/沙魏马`——正文只有标题没有表格（0 行），被**静默丢弃**（连 warning 都没有）。速览与正文的权威性被混用：速览既当白名单又当「名单」，`make-questionnaire.js` 则把速览当**全量替换**（`:40`），导致问卷展示 35 支 T1、`plan5` 只能规划 30 支（见 P1-12）。

**缺陷**：
- 只读 4 列，第 5 列「词条」（天资/良止/英勇…）完全没有进入数据结构；而强度榜的宝物价值很大程度在词条上（P1-3）。
- 状态机是单遍的（`:71-102`）：如果某天出现「速览有、正文标题名不完全一致」的情况，`cur` 会停留在上一队，后续表格行会继续 push 进上一队的 `heroes` 缓冲，造成「队名 A + 武将 B」的错配（当前文件 0 例，属脆弱点，P2-1）。
- 队名在速览里重复会按分档各建一次（实测 `属性刀` 同时出现在 T0 与 T2-，两支队武将不同：`汉荀彧/沮授/张宁` vs `张宁/张昭/刘表`），文档里无法区分。

### 3.2 版本/阵营校验：三张表 + 三个数据源

- **四态判定**：`planAccount`（`plan5-core.js:180-184`）`land = 完整 3 / 只缺宝 2 / 缺战法 1 / 都缺 0`，`Score = tierScore + land`（`:185`）。`landStatusList`（`:197-217`）只分 3 桶，**「都缺」被塞进 `missTac`**（`:214`）→ `land-stats.js:33`/`recommend.js:61` 的 `missTacCount` 实际是「缺战法 + 都缺」，与 `plan5-node.js:41-44` 的四态输出不一致（P1-9）。

### 3.6 5 队组合最优 `bestCombination()`（`plan5-core.js:134-162`）

- 枚举：从 `maxK2=min(5,n)` 向下，`dfs` 组合枚举，`k` 从大到小，**第一个找到合法组合的 k 就 break**（`:156-160`）。因为 `Score>=1` 恒成立（tierScore 最低 1），多做一队总不加分也至少不扣分，所以「最大可组数 + 在该 k 下取最大总分」在数学上是正确的（任何 k 组合都含 k-1 子集，可行性单调），这里没有问题。
- 实现细节问题：
  1. **冲突检测用原始队名，不用归一化名**（`:146,148` 用 `c.Heroes` 而非 `normHero`）→ 别名可绕过「武将不重复」。实测 186 号里有 **2 个号真的组出了重复武将**：`X5829 ¥1,500` 同时用 `周瑜` 与 `XP周瑜`（斩龙刀/干锅队/胜兵嘟嘟/吴之智/太监队），`X5864 ¥1,600` 同时用 `SP赵云` 与 `赵云`（定军赵/斩龙刀/枭雄太刀/属性刀/蜀刀）。这两份「最佳 5 队」直接违反输出标题（`plan5-node.js:2`「武将不重复」）。
  2. 无剪枝、无 tie-break：`sc > bestScore`（`:151`）严格大于，同分保留先枚举到的组合 → **结果依赖榜单行序**，榜单改动顺序会改变 5 队输出。
  3. `combos` 只统计最后一层 k 的组合数（`:142`），且无上限保护；当前 `cand` 最大 27（实测），`C(27,5)=80730`，性能尚可，但若将来「跳过规则」被修好、`cand` 涨到 40+，会到 `C(40,5)=658008` 量级（`plan5-v2.ps1` 时代 128 号 50 秒的来源）。
  4. 同一函数在 `recommend.js:107` 对 Top20 号又重算一遍（land-stats 只导出计数），纯重复计算。

### 3.7 `recommend.js` 的排序与文档生成

- **排序键**（`:70-72`）：`full*1000 + onlyGear*100 + (full+onlyGear+missTac)`。`武将分`（`:62`）与价格都没进排序键；文案 `:80` 写「完整队数 → 只缺宝队数 → 可组总数 → 武将分」，copilot 第 33 行还要求「短期强度接近时优先选便宜的」→ 两条都没落地。
- **武将分来源**：`data/tmp/analyze-latest.txt`（PS 分析链产物，另一任务范围）用正则抓（`:45-49`）。该文件实测 186 行、**只有 163 个 `server-price` 键**，`recommend.js:48,62` 用 `server-price` 作 key → `X5882-2000` 实际有 90/68 两条、`X5849-2500` 有 68/44/26 三条，**后者覆盖前者**，分数串号（实测 12 组冲突示例，18 组总数）。这既错用数据，也让 `recommend.js` 隐式依赖 PS 输出格式（正则耦合，无版本号）。
- **价格过滤单位**：`:18-19` 默认 `1500-2000`（元），而 `find-all.ps1:19-20` 采的是 150000-250000（分，=1500-2500 元）→ 自动建议默认只覆盖采集区间的下 2/3，且无提示；文档头部（`:79`）却写「基于 163 个账号(1500-2000 档)」，读者会以为这就是全量。

- **文档口径**：`:81` 声称「版本硬校验: 曹操=魏 / 关羽=蜀 / 赵云=SP / 汉荀彧=汉」——前三项成立，`汉荀彧` 因表里是 `汉苟彧` 从不生效（P0-2）；`:129`「下单前建议对 Top 3 浏览器复核」是诚实的兜底，但 `browser-verify.js` 本身只核武将不核战法/宝物（P1-10）。

### P0-1 含 `司马懿`/`弓诸葛` 的队伍被整队跳过（12 队，含 4 支 T0+）
- 位置：`plan5-core.js:176`（`planAccount`）、`plan5-core.js:208`（`landStatusList`）。
- 触发条件：任何队伍三名武将中出现字面 `司马懿` 或 `弓诸葛`（榜单当前 8 + 4 = 12 支）。
- 影响：这些队**不进入 `cand`、不计完整/只缺宝、不参与 5 队规划**。T0+ 的直接损失：`变种王异刀`、`庞统蜀步`、`九伐队`、`张飞流氓` 全部消失。「弓箭塔/司马体系」是当前榜单 T0+ 的主体，等于是把最强档砍掉 40%。文档要的是版本校验（`copilot:18-20`、`SKILL.md:47`），实现成了「不评估」。
- 证据：实测 101 队中 12 队命中此规则；`data/tmp/analyze-latest.txt`（PS 路径，不做整队跳过）把 `X5882 ¥2,000` 打到 90 分并列出 2 支 T0+，而 JS 路径同一号只有 3 支完整队（T1/T2-）——两条链结论冲突，自动建议采用后者。
- 修复方向：不要删队；把「晋/汉/魏」等版本标记补进上游 `marks`（`name-camp` 或 `HERO_SPECIAL` 补 `晋`），用 `VersionReq['司马懿']='晋'` 做校验；`弓诸葛` 同理（榜单只用这一个名字，账号侧若无对应武将则应显式记 `no-hero` 而不是丢队）。

### P0-2 榜单→账号的别名/版本标记层系统性缺失（38/101 队结构性不可组）
- 位置：`plan5-core.js:39-53`（`VersionReq`/`NormalizeMap`）、`merge-api.js:20-32,54-58`（`HERO_SPECIAL`/`name-camp`）、`plan5-core.js:107-120`（匹配）。

  - 缺键：`汉董卓`（表里只有 `汉董`，`:40,48`）、`群吕`/`群绍`、`苟彧`（OCR，从未映射到 `荀彧`）、`XP陆逊`、`马妹`、`月英`、`春华`、`关张`、`大小乔`、`木鹿/曹仁`（单元格两名武将）。
