# 率土之滨找号仓库 · 全方位优化调研（2026-10-25）

> 调研方式：静态审读 31 个脚本 + 40 个 docs 文件 + 数据实测（186 号 / 129 条 API / 126 行浏览器数据）
> + 运行验证（`strategy-eval`、`report.ps1`、`npm run`、`node --check`）。
> **未触发任何采集、未登录藏宝阁、未修改业务数据**；测量输出均写临时目录或已清理。
> 调研只回答「哪里可以优化、优先级如何」，不在本轮改代码。

---

## 0. TL;DR

仓库已经能跑通「白名单 → 采集 → 合并 → 评估 → 报告」全链路，且最近补了试师白名单自动更新、预筛分、配置化策略等新能力。但调研发现 **6 个会直接让结果失真的 Bug 级问题**、**4 个高概率运行翻车点**、以及明显的工程债（三套评分权并存、测试只覆盖白名单、26 项核心改动未提交）。

按影响排序，最该先修的 6 件事：

| # | 问题 | 一句话影响 | 工作量 |
|---|------|-----------|--------|
| 1 | 三套队伍评分权重互不一致 | 同一账号在「找号报告」和「策略排序」里名次不同，结论自相矛盾 | 0.5 天 |
| 2 | `merge-api` 阈值写死 85/12，与配置（稀世≥10）脱节 | 10–11 个稀世宝物的候选在合并阶段被静默剔除 | 0.5 小时 |
| 3 | 榜单武将名未归一化（苟彧/春华/群绍/木鹿/曹仁…） | 101 队里 27 队永远匹配不到任何账号，强队被系统性低估 | 0.5 天 |
| 4 | 按「区服+价格」去重 | 186 号里 22 个号在推荐链路被当重复丢掉 | 1 小时 |
| 5 | 旧的 8 月浏览器数据默认混入且不刷新 | 报告可能推荐已下架/已改价的号，且状态字段缺失 | 0.5 天 |
| 6 | 配置不是单一来源（list-filter/collect/cbg-extract 各自写死阈值） | 改配置不生效或部分生效，容易再制造 #2 类 Bug | 0.5 天 |

## 2. 发现（按维度）

### 2.1 准确性（Bug 级，直接让结论失真）

#### A1. 三套队伍评分权重，同一账号三种名次

| 脚本 | 权重 | 位置 |
|------|------|------|
| `analyze-accounts.ps1`（找号报告用） | T0+ 10 / T0 8 / T0- 6 / T1 3 / T2- 1 | `scripts/analyze-accounts.ps1:178` |
| `plan5-core.js`（plan5 / recommend 用） | T0+ 8 / T0 7 / T1 3 / T2- 1（**无 T0-**） | `scripts/plan5-core.js:179` |
| `strategy-config.json`（策略评估用） | T0+ 10 / T0 8 / T1 5 / T2- 2 | `data/strategy-config.json:51-55` |

三处分数都进排名，导致 `docs/找号报告-*.md` 与 `reports/策略落地-*/策略排序.md` 对同一账号排序不一致；用户拿两份报告对照会直接困惑。另外 `plan5-core` 还整队跳过司马懿/弓诸葛（`:176,208`），而 `strategy-eval` 用 versionOverrides 允许司马懿，口径再次分叉。

**建议**：只保留一份「tier 权重 + 跳过规则」配置，PS/Node 全部读取；`plan5-core` 删除硬跳，改用配置。

#### A2. `merge-api` 硬编码 85/12，配置改了不生效

- 位置：`scripts/merge-api.js:77` `if (heroes.length < 85 || equips.length < 12)`。
- 配置已是 `fiveStarMin: 85, rareEquipMin: 10`（`data/strategy-config.json:23,28`），且 2026-10-25 二次优化结论就是「稀世 12→10，召回 1 个候选」。
- 后果：API 补采路径的号只要稀世 10–11 个就在合并时被剔除，**二次优化的收益在主链路被吞掉**。历史样本里确实有 1 个候选因此被排除。

同类：`cbg-detail-extract.js:25` 的默认 URL 仍写 1500–2500 / 85 / 12；`collect.ps1:9-10` 参数默认 85/12。

**建议**：所有阈值从 `strategy-config.json` 读取，缺配置即报错而不是静默用默认值。

#### A3. 榜单武将名未归一化 + 合并单元格，27/101 队永远匹配不到

- 归一化表 `scripts/plan5-core.js:47-49` 覆盖有限；榜单里大量别名：
  `苟彧`（应=荀彧，`docs/队伍强度排行榜.md:625`）、`春华`（张春华）、`群绍`（袁绍）、`XP陆逊`（陆逊）、
  `关妹`（关银屏）、`马妹`（马云禄）、`月英`（黄月英）、`凡突骨`（兀突骨）等。
- 合并单元格：`docs/队伍强度排行榜.md:626` 的 `木鹿/曹仁` 被解析成单一武将，直接废掉衡轭队。
- 实测：101 队中 27 队至少一个武将名在 186 号数据里从未出现；补 11 条别名后「完全可匹配」的队从 **74 → 91（+17 队）**。
- 模拟副作用：全部账号的落地队计数都会变化，full+onlyGear 从 576 → 772（**上限值**，因为部分别名应带版本标记，如 群吕/汉荀彧，不能简单映射到基础名）。

**建议**：别名表补全且与版本要求成对维护；合并单元格（木鹿/曹仁、关张、大小乔）单独建模；解析后加自检（每档队数 vs 速览行、异常武将名告警）。这是**单点收益最大的准确性修复**。

#### A4. 按「区服+价格」去重，22 个号被当重复丢掉

- `scripts/recommend.js:35-36` 用 `server-price` 做 key；`scripts/cbg-detail-extract.js:209,245` 与 `scripts/collect.ps1:54` 同款逻辑。
- 实测：186 号里不同 ordersn 但同区服同价格的有 **22 个号**会被判重丢弃（历史统计 23 个，口径一致）。
- 后果：最终购买建议少看 22 个号，候选可能整只被隐藏。

**建议**：统一按 `ordersn` 去重；`server-price` 仅用于页面回填展示。

#### A5. 8 月旧浏览器数据默认混入、不刷新

- `find-all.ps1:26-28`：只要 `data/accounts-detail-1500-2500.json` 存在就自动当 `BrowserFile` 传入 → `api-collect` 跳过这 117 个 ordersn（补漏模式）。
- `merge-api.js:42-48`：按**文件体积最大**挑浏览器文件（不是最新/本批次），当前挑中的正是 8 月旧文件。
- 后果：默认跑一次 10 月采集，最终数据里 117/186 是 8 月旧价格、旧状态；若这些号已下架/改价，推荐会失真。
- 且 `merge-api.js:82` 把 API 数据的 status 写成 `''`，而浏览器行保留 `公示期/上架中`，状态口径也不一致。

**建议**：显式 `-BrowserFile`/按 mtime+批次清单选择；默认不混入历史文件；报告中标注每个号的数据时间与来源。

#### A6. 没有在售状态过滤，也可能推荐已售号

- `strategy-eval.js` / `recommend.js` 均不检查 `overview.status`；186 号里 69 个 status 为空、15 个公示期。
- 后果：报告和最终建议可能包含已下架/已售出的号（8 月数据尤其危险）。

**建议**：报告顶部标注「快照时间 + 状态分布」；推荐前过滤 `已售出/已下架`，公示期单列提示。

#### A7. 配置不是单一来源（漂移风险）

| 位置 | 写到 | 与配置对照 |
|------|------|-----------|
| `scripts/list-filter.js:17` | DEFAULT_L2 = 90/22/15/12 | 配置 85/20/15/10；配置缺失时静默回退旧值 |
| `scripts/list-filter.js:48-49` | 对照实验 70/85、5/12 硬编码 | 与配置无关 |
| `scripts/cbg-detail-extract.js:25` | URL 85/12 | 缺 forged/rare 区分 |
| `scripts/collect.ps1:9-10` | 参数默认 85/12 | 同上 |
| `scripts/filter-strategy.js:217-220` | 报告文本写死 85/20/15/12 | 与配置 rare=10 不一致 |
| `scripts/fill-test-questionnaire.js:27,29` | 问卷写死 85/12 | 同上 |

**建议**：做 `config` 读取入口（Node/PS 各一个），所有脚本引用；启动时打印生效参数；配置缺失直接报错。

### 2.3 性能 / 成本

| 项 | 实测 | 评价 |
|----|------|------|
| `strategy-eval.js`（186 号） | **0.2s** | 很好 |
| `report.ps1` 全链（3 个子进程） | **7.4s** | 可优化：PS 重复解析榜单 + 3 次进程启动 |
| 详情采集 | 每号 sleep 3–4s + 请求（`api-collect.js:250`） | 150 号 ≈ 8–10 分钟；已有「并发>3 触发 eb-re410」教训，**不建议提并发** |
| 列表翻页 | 每页 800ms（`:151`） | 300 条以内无压力 |
| 仓库数据 | `data/` 已追踪 9.5MB（其中 accounts-api 4.45MB、final 1.9MB、bak 1.3MB） | 快照进 git，随每次采集膨胀 |

可优化点：
1. 报告链 Node 单进程化（复用 `plan5-core` 已解析的榜单），预计 7.4s → <1s。
2. 采集「列表阶段预筛分 + topN」已落地，继续用；别动并发。
3. 大 JSON 归档策略（按批次存 gzip 或移到 `reports/` 外），避免仓库无限膨胀。

### 2.4 可维护性 / 工程化

- **31 个脚本无分层**：明显历史/一次性脚本有 `plan5-v2.ps1`、`lib-cbg.ps1`（只被 plan5-v2 引用）、`count-teams.ps1`、`t0-stats.ps1`、`t0-hero-count.ps1`、`find-accounts-20260807.ps1`、`fetch_cbg_api.ps1`、`page-list-collect.js`；没有 `scripts/legacy/` 或说明。
- **无 README**（根目录无 README.md）；唯一全局说明是 `.github/copilot-instructions.md`（旧的评分描述已与 `strategy-config.json` 不一致）。
- **docs/ 40 个文件 708KB**，规范/一次性报告混放；单文件最大 `docs/找号报告-自用-20260807.md` 278KB；`reports/` 与 `docs/` 用途边界模糊。
- **26 项改动未提交**（11 modified + 15 untracked），包括全部 10-25 新交付（`update-shishi.js`、`strategy-eval.js`、`strategy-config.json`、`reports/` 等）——丢失风险高；仓库无 `.gitattributes`。
- **配置无 schema/校验**，且存在冗余键（`coreHeroHitsMin`、`maxDetailCandidates`、`l1_pool.bargainLine`、`l4_manual_check` 等使用情况不一致）。
- **数据无 provenance**：accounts-final 不记来源（API/浏览器）、采集时间、run 参数、config 版本；出问题无法复现。

### 2.5 数据 / 知识库

- `docs/队伍强度排行榜.md` 最后维护于 **2026-08-07**（101 队），当前已是 10 月底、经历新赛季；新武将（司马炎/羊祜/杜预/王元姬/卫瓘…）与版本变动未纳入。榜单是评分核心输入，**陈旧=结论陈旧**。
- 榜单为人工维护的 Markdown，解析器对格式极敏感（别名、合并单元格、速览/详情不一致都会静默丢队）；且 `plan5-core` 与 PS 各有一份解析实现（双份 drift）。
- `data/name-camp.json` 仅 2.5KB，29 个武将名缺阵营映射；API 路径靠 `HERO_SPECIAL` hero_id 特判（`merge-api.js:20-32`）兜底，新增武将只走名字表时会 camp='' → 版本校验失败 → 队伍被跳过（静默）。
- 战法简称表 `TacticMap` 57 项人工维护（`plan5-core.js:16-36`），新战法不补 → 队伍误判缺战法。

**建议**：榜单迁 `data/teams.json`（保留 md 作为人读文档，由 JSON 生成或校验）；加 schema+自检；新武将/新战法进数据文件而不是代码。

### 2.6 体验 / 报告

- 报告是单个超大 Markdown（`docs/找号报告-自用-20260807.md` 278KB），无「一分钟摘要」；最终购买建议另发文件，需来回切换。
- 报告未标注数据快照时间、在售状态、价格口径（分/元）——用户容易按旧快照决策。
- 候选很少时没有「放宽建议/替代价位」；问卷与筛选参数脱节（问卷写死 85/12）。
- Skill 有 280 行，流程长但可用；可作为「人读手册」保留，但需与配置同步。

## 4. 优化方案（分层）
