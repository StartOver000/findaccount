# 锻造门槛 A/B 复测（2026-10-25）

> 问题：列表服务端参数 `duanzao_gear_cnt=15` 是否卡掉了好号？关掉后是否值得？
> 结论：**单时点、1500–2500 价格区间内没有发现被隐藏的头部候选，保留 `forgedGearMin=15`**；关掉只多出 25 个弱号，反而每次多付约 25 个详情请求。

## 方法

- 采集入口：`scripts/api-collect.js`（CBG 列表 `recommd_by_role` + 详情 `get_equip_detail`），试师开放服 65 个（`data/shishi-open.json`），价格 150000–250000 分。
- 对照组（主池）：现行门槛 五星≥85 + 锻造≥15 + 稀世≥10 + S 战法≥20，2026-10-25 20:05 采集，列表 35 卡 → 详情 33（2 个 S 战法<20 被 L2 挡）。
- 实验组（关锻造）：`data/tmp/config-noforged.json`（复制主配置，仅 `l2_list_filter.forgedGearMin=0`），通过 `STZB_CONFIG` 环境变量覆盖配置路径；同价格区间、同一批试师服，20:51–20:55 采集。
  - 先验证过：CBG 服务端把 `duanzao_gear_cnt=0` 当作「不过滤」（与不传该参数返回相同）。
- 评估口径：`scripts/strategy-eval.js`（统一评分引擎 + 缺战法分级曲线）与 `data/tmp/compare-noforged.js`，主池 `data/accounts-final.json`（162 号）对照实验池 `data/accounts-final-noforged.json`（58 号）。

## 结论与决策

1. 在 1500–2500 区间、当次在售样本里，锻造≥15 **没有隐藏头部候选**：关掉后新增的 25 个号最强仅 67.7，过 gate 的最强 57.3。
2. 保留 `forgedGearMin=15`：每次列表→详情少约 25 个请求（详情 3–4s/号，约 1.5–2.5 分钟），且预筛分排序不变、召回无损。
3. 锻造门槛的定位仍是「服务端低成本压缩列表 + 详情预算/限流 + 练度代理」，不是评分门槛（`l3_scoring.gate` 不看锻造）。
4. 需要放宽时不必改默认值：临时把 `forgedGearMin` 置 0（或未来用 `STZB_CONFIG` 指向实验配置）跑对照即可。

## 局限

- 单时点 A/B（20:47–20:55），实验池仅 58 个详情；捡漏线 1200–1500 未做对照，低档位结论不能直接外推。
- API 列表 desc 没有锻造字段，客户端无法复核锻造数，只能依赖服务端过滤。
- 当前 `api-collect` 实际未强制执行 `detailBudget=40`（L2 通过的 58 个全抓了）；若未来加严详情预算，这次 A/B 的「多付 25 个详情」成本会下降，但结论方向不变。
